사내메신저 배포 결정사항 체크리스트
====================================

목적
----
실제 배포를 시작하기 전에 제품 공개 범위, 호스팅, 데이터 보존, 보안, 비용과 운영 방식을 결정하기 위한 목록이다.
이 문서는 선택지를 정리한 것이며, 플랫폼을 선택하거나 배포 설정을 만들거나 실제 배포를 수행하지 않는다.


현재 프로젝트 상태
------------------
- 프런트엔드: React + Vite. `npm run build` 결과물은 `dist/`에 만들어진다.
- 백엔드: Java 21 + Spring Boot + Gradle. 기본 포트는 8080이다.
- 개발 DB: `data/sinae-messenger.db` 파일을 사용하는 SQLite.
- 로컬 개발 시에만 Vite가 `/api` 요청을 `localhost:8080`으로 전달한다. 이 Vite proxy는 운영용 설정이 아니다.
- 세션 로그인과 CSRF 보호를 사용한다. 별도 세션 저장소 의존성은 없으므로 서버 메모리에 세션이 저장된다.
- DB 스키마는 Hibernate `ddl-auto=update`로 자동 갱신된다. 별도 마이그레이션 도구는 확인되지 않았다.
- `DB_URL`, `SERVER_PORT` 환경 변수 설정이 있다. 운영용 도메인·TLS·정적 파일 제공·모니터링 설정은 확인되지 않았다.
- 저장소에서 플랫폼 배포 설정과 CI/CD 설정을 확인하지 못했다.
- Docker는 사용하지 않는 것으로 확정되어 있다.
- 공개 채널 메시지 MVP이며, 친구·개인 메시지·첨부 파일·관리자 기능은 범위에서 제외되어 있다.


1. 공개 범위와 서비스 운영 목적
-------------------------------
[ ] 서비스 공개 대상: 나만 사용 / 초대한 사람만 / 누구나 가입 가능
[ ] 서비스 목적: 학습·포트폴리오 / 실제 지속 운영
[ ] 공개 시 표시할 서비스명과 소개 문구
[ ] 이용 규칙, 개인정보 안내, 문의 연락처를 게시할지
[ ] 가입을 공개할지 결정한다. 현재 회원가입 API는 공개 요청을 받으며 가입 제한·속도 제한 기능은 확인되지 않았다.
[ ] 메시지와 계정 데이터를 얼마 동안 보관하고, 사용자 요청 시 어떻게 삭제할지

결정 영향: 누구나 가입하도록 공개하면 스팸·악성 입력 대응, 서비스 중단 및 계정 데이터 관리가 필요하다.


2. 호스팅 위치·방식·비용
------------------------
[ ] 호스팅 위치: 클라우드 플랫폼 / 개인 서버 / 기타
[ ] 후보 플랫폼과 선택 이유
[ ] 사용할 리전(서버 지역)과 예상 사용자 지역
[ ] 무료 한도만 사용할지, 유료 요금제를 허용할지
[ ] 월별 비용 한도: __________
[ ] 결제 수단 등록 또는 자동 과금 허용 여부
[ ] 플랫폼 계정·프로젝트 소유자와 접근 권한
[x] Docker 미사용

플랫폼 선택 전 확인할 점:
- Java 21 Spring Boot 프로세스를 직접 실행할 수 있는지
- 영구 디스크를 제공하는지, 용량·비용·백업 조건은 무엇인지
- 앱이 절전·중지되는 무료 요금제인지, 첫 요청 지연이나 사용 제한이 있는지
- HTTPS, 사용자 도메인, 로그, 배포 취소 기능을 제공하는지
- 서비스 삭제나 요금제 변경 때 DB 파일을 내려받을 수 있는지


3. 프런트엔드와 백엔드 배치
---------------------------
[ ] 두 부분을 한 도메인에서 제공 / 프런트엔드와 API를 각각 다른 도메인에서 제공
[ ] 프런트엔드 빌드 `dist/`를 Spring Boot가 제공하도록 구성 / 정적 사이트 호스팅 사용
[ ] 운영에서 `/api`를 백엔드로 전달할 reverse proxy(요청 중계 서버)를 사용할지
[ ] API 문서 Swagger UI를 공개할지, 비공개로 둘지

검토안(아직 미확정): 한 도메인으로 제공하면 세션 쿠키·CSRF·브라우저 교차 출처 설정을 단순하게 유지하기 쉽다. 하지만 현재 Vite proxy는 개발용이고, Spring Boot가 `dist/`를 제공하도록 구성되어 있지 않으므로 운영 연결 방식 구현이 필요하다.

서로 다른 도메인을 선택하면 CORS, 쿠키의 SameSite/Secure 설정, 자격 증명 포함 요청, CSRF 토큰 전달을 추가로 맞춰야 한다.


4. 운영 데이터베이스와 영구 저장
-------------------------------
[ ] 운영에서도 SQLite 사용 / 운영 DB를 PostgreSQL·MySQL 등으로 변경
[ ] 앱과 DB 파일을 같은 서버의 영구 디스크에 둘지
[ ] SQLite 선택 시 단일 앱 인스턴스만 운영할지
[ ] DB 파일의 저장 경로와 디스크 마운트 위치
[ ] 백업 주기: __________
[ ] 백업 보관 기간: __________
[ ] 백업 파일 접근·암호화 방법
[ ] 복원 연습 주기와 복원 책임자
[ ] 데이터 유실 허용 범위와 복구 목표

SQLite 검토안(아직 미확정): 작은 단일 인스턴스 서비스에는 구성 요소가 적어 가볍다. 단, 앱 재시작·재배포 후에도 파일이 유지되는 영구 디스크가 반드시 필요하고, 여러 서버가 같은 SQLite 파일을 동시에 쓰는 구성을 피해야 한다. 플랫폼 저장소가 임시 파일 시스템이면 SQLite 운영을 선택하지 않는다.

운영 DB를 변경하면 드라이버·Hibernate 설정, 데이터 이전, 백업·비용 검토와 테스트가 추가로 필요하다.


5. 계정·세션·웹 보안
---------------------
[ ] 기본 admin 계정 비밀번호를 공개 전에 변경하거나 계정을 비활성화한다.
[ ] 현재 admin 계정에는 관리자 전용 역할·관리 API가 없다. admin이라는 아이디만으로 관리자 기능이 생기지 않는 점을 확인한다.
[ ] HTTPS 사용 여부와 인증서 발급·갱신 담당
[ ] HTTPS 뒤에서 세션 쿠키의 Secure 옵션을 켜는 방법
[ ] 운영 도메인에서 세션 쿠키의 HttpOnly, SameSite 정책 확인
[ ] 세션 만료 시간과 서버 재시작 후 로그아웃을 허용할지
[ ] 단일 인스턴스로 운영할지, 여러 인스턴스·공유 세션 저장소가 필요한지
[ ] CSRF 토큰과 인증 쿠키가 운영 도메인에서 동작하는지 검증
[ ] 가입·로그인 시도 제한이나 스팸 대응이 필요한지
[ ] 보안 오류·계정 공격 징후를 누가 확인할지

현재 세션은 서버 메모리에 저장된다. 서버 재시작 시 로그인 세션이 사라지고, 여러 인스턴스를 쓰면 세션 공유 구성이 없어 인증이 불안정해질 수 있다. 가벼운 단일 인스턴스로 갈지, 세션 저장소를 추가할지 결정한다.


6. 비밀값과 환경 설정
---------------------
[ ] 운영 설정은 플랫폼 환경 변수 또는 비밀 저장소에 입력한다. 비밀값을 저장소 파일·Git·로그에 넣지 않는다.
[ ] `SERVER_PORT`: 플랫폼에서 지정한 포트에 맞춘다.
[ ] `DB_URL`: SQLite 파일 경로 또는 선택한 운영 DB 접속 주소를 지정한다.
[ ] 운영 DB를 별도 선택하면 DB 사용자명·비밀번호 등 추가 환경 변수가 필요하다.
[ ] 개발·테스트·운영 프로필의 설정 분리 방법
[ ] 로그에 비밀번호, 세션 ID, CSRF 토큰, DB 접속 정보가 기록되지 않는지 확인


7. DB 스키마·배포 절차
----------------------
[ ] 운영 DB의 자동 스키마 갱신을 허용할지 결정한다. 현재 설정은 `ddl-auto=update`다.
[ ] 운영 스키마를 수동 관리할지, Flyway/Liquibase 같은 마이그레이션 도구를 도입할지
[ ] 배포 전 백업 수행 및 마이그레이션 실패 시 되돌리는 절차
[ ] 기존 SQLite 데이터가 있으면 계정·채널·메시지 이전 여부와 검증 방법
[ ] 배포 단위: 수동 빌드·업로드 / Git 연동 자동 빌드
[ ] 사용할 Java·Gradle·Node 버전과 프런트 빌드 실행 순서
[ ] 배포 전 검증 및 배포 후 smoke test 담당자
[ ] 문제가 생겼을 때 이전 버전으로 되돌릴 방법


8. 상태 확인·장애 대응·비용 통제
--------------------------------
[ ] 앱 상태 확인(health check) 주소와 주기
[ ] 현재 모니터링·health check 구성이 없으므로 플랫폼 기본 기능으로 충분한지, 엔드포인트가 필요한지
[ ] 로그 보관 기간, 접근 권한, 확인 담당자
[ ] 앱 오류·서비스 중단 알림을 받을 방법
[ ] DB 용량·디스크 사용량·백업 실패 확인 방법
[ ] 월 사용량과 결제 한도 알림
[ ] 장애 시 사용자 안내와 복구 담당자
[ ] 서비스 종료 시 DB 백업, 도메인 해제, 계정·자원 삭제 절차


9. 배포 전 기능 검증
--------------------
[ ] 회원가입, 중복 가입, 로그인 실패, 로그아웃
[ ] 닉네임 변경 후 과거 메시지에 새 닉네임 표시
[ ] 채널 목록·메시지 조회·메시지 작성·polling
[ ] 비로그인 사용자의 보호 API 접근 거부
[ ] CSRF 오류와 인증 만료 처리
[ ] HTTPS에서 로그인·쿠키·새로고침 동작
[ ] 앱 재시작 뒤 계정·채널·메시지 데이터 유지
[ ] 백업 파일로 실제 복원 가능한지
[ ] 모바일 화면과 기본 접근성 확인
[ ] 운영 환경 변수에 비밀값이 안전하게 설정됐는지


10. 실제 배포를 시작하기 위해 사용자가 정할 항목
-------------------------------------------------
1) 서비스 공개 대상(개인 / 초대 사용자 / 전체 공개)
2) 호스팅 플랫폼·서버 위치
3) 월 비용 허용 한도와 유료 자원 사용 여부
4) 도메인 사용 여부와 DNS 변경 승인 여부
5) 프런트엔드/API를 한 도메인으로 제공할지
6) 운영 DB: SQLite 영구 디스크 / 관리형 DB
7) 기본 admin 계정을 교체·비활성화할지
8) 단일 인스턴스와 메모리 세션 손실을 허용할지
9) 백업 주기·보관 기간·복구 목표
10) 자동 배포를 허용할지, 수동 배포를 사용할지
11) Swagger 문서 공개 여부
12) 외부 업로드·클라우드 자원 생성·공개 배포에 대한 별도 명시적 승인

현재 Docker 미사용은 확정되어 있다. 그 밖의 선택 항목은 이 문서에서 임의로 확정하지 않는다. 외부 배포는 선택 항목이 결정되고 사용자가 배포 범위를 명시적으로 승인하기 전에는 수행하지 않는다.
