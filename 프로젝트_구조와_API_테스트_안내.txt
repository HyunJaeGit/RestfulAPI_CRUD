사내메신저 프로젝트 구조·API·테스트 입문 안내
작성 기준: 현재 저장소의 Gradle 설정, Spring Boot 소스와 테스트 코드

============================================================
1. 프로젝트 한눈에 보기
============================================================

사내메신저는 브라우저에서 회원가입·로그인하고 공개 채널의 메시지를 읽고 작성하는 웹 애플리케이션이다. 저장소에는 Spring Boot 백엔드와 React/Vite 프런트엔드가 있다. DB를 준비하기 전에도 메모리 기반 mock API를 사용해 프런트 흐름을 확인할 수 있다.

현재 기술 구성
- 백엔드: Java 21, Spring Boot 3.5, Gradle
- HTTP API: Spring Web, JSON 요청·응답
- 데이터 접근: Spring Data JPA와 Hibernate
- 개발·테스트 DB: SQLite 파일
- 로그인: Spring Security 세션 쿠키, 비밀번호 BCrypt 해시
- API 설명서: springdoc OpenAPI / Swagger UI
- 백엔드 테스트: JUnit 5, Spring MockMvc
- 프런트 mock 테스트: Node.js 내장 `node:test`
- 실행 방식: 로컬 프로세스 직접 실행. Docker는 사용하지 않는다.

애플리케이션은 하나의 Spring Boot 프로세스로 실행되는 백엔드다. SQLite 파일은 기본적으로 data/sinae-messenger.db에 저장되고, 테스트는 data/sinae-messenger-test.db를 사용하도록 분리돼 있다.

요청이 처리되는 큰 흐름은 다음과 같다.

브라우저(React)
  → Vite 개발 서버의 /api proxy
  → HTTP 요청(JSON)
  → API Controller
  → Service의 업무 규칙
  → Repository / JPA
  → SQLite
  → 응답 DTO(JSON)

예를 들어 메시지를 보낼 때 Controller는 요청을 받고, Service는 채널 존재 여부와 닉네임 설정 여부를 확인하고, Repository가 DB에 저장한다. 결과는 MessageResponse라는 응답 형태로 브라우저에 돌아간다.

============================================================
2. 소스코드 폴더를 나눈 이유와 각 역할
============================================================

src/main/java
  실제 애플리케이션 Java 소스가 들어가는 표준 Gradle 폴더다. main은 제품 실행 코드라는 뜻이다. 그 아래 Java package 경로는 역할별 코드를 찾고 이름 충돌을 막기 위한 구분이다.

com/sinae/messenger
  기본 package다. SinaeMessengerApplication.java가 Spring Boot 시작점이다. 이 package의 하위 package들을 Spring이 찾아 컴포넌트로 등록한다.

com/sinae/messenger/api
  HTTP API 입구와 출구를 모아 둔다.
  - AuthController: CSRF 토큰, 회원가입, 로그인, 로그아웃, 현재 사용자
  - UserController: 닉네임 변경
  - ChannelController: 채널 목록
  - MessageController: 메시지 조회·작성
  - SignupRequest, MessageRequest 등: 요청 필드와 입력 검증 규칙
  - AuthResponse, MessageResponse 등: 클라이언트에 내보낼 응답 구조
  - ApiExceptionHandler: 검증 오류나 업무 오류를 공통 JSON 오류 응답으로 변환

  Controller는 HTTP 연결을 처리하는 얇은 층이다. DB 조회나 복잡한 업무 규칙을 여기에 몰아넣지 않고 Service에 맡긴다.

com/sinae/messenger/user
  계정과 사용자 닉네임에 관한 코드다.
  - UserAccount: 사용자 DB 모델(Entity)
  - UserRepository: 사용자 저장·조회
  - AccountService: 회원가입, 비밀번호 해시, 닉네임 변경
  - RepositoryUserDetailsService: Spring Security가 로그인 ID로 계정을 찾을 때 사용

com/sinae/messenger/channel
  공개 채널의 DB 모델, 조회 기능, 기본 채널 준비 코드를 둔다.
  - ChannelEntity: 채널 데이터
  - ChannelRepository: 채널 DB 조회
  - ChannelService: 채널 목록과 존재 확인
  - ChannelInitializer: 처음 실행할 때 general, random 채널을 없으면 생성

com/sinae/messenger/message
  메시지 데이터와 메시지 업무 규칙을 둔다.
  - MessageEntity: 내용, 채널, 작성자, 작성 시각
  - MessageRepository: 메시지 저장과 채널별 조회
  - MessageService: 메시지 검증, 작성, 새 메시지 조회

  MessageEntity가 작성자 UserAccount를 참조한다. 화면에 작성 시점의 닉네임 문자열을 복사해 두지 않으므로 닉네임을 바꾸면 과거 메시지 조회에도 새 닉네임이 표시된다.

com/sinae/messenger/security
  인증과 보안의 공통 설정을 둔다. SecurityConfiguration에서 세션 인증, 비밀번호 검증기, CSRF 보호, 로그인되지 않은 요청의 401 응답 등을 구성한다.

src/main/resources
  실행 시 읽는 설정 파일이 있다. application.properties에서 포트, SQLite 주소, Hibernate 동작, 세션 쿠키와 Swagger 설정을 관리한다. 환경에 따라 달라질 값은 DB_URL, SERVER_PORT 같은 환경 변수로 덮어쓸 수 있다.

src/test/java
  자동화 테스트 코드가 들어간다. 현재 ApiFlowTests.java가 회원가입부터 로그인, 닉네임 변경, 메시지 작성과 오류 응답까지 API 흐름 일부를 확인한다.

src/test/resources
  테스트에서만 적용할 설정이다. application.properties가 테스트 DB 경로를 개발 DB와 다르게 지정하고 Swagger를 끈다. 테스트가 개발 데이터를 지우거나 섞지 않도록 분리하는 목적이다.

src/main.jsx
  React 앱을 HTML의 root 요소에 연결하고 전역 CSS를 불러오는 프런트엔드 진입점이다.

src/ui
  - App.jsx: 로그인, 닉네임 설정, 채널 목록, 채팅 화면과 화면 상태
  - styles.css: 터미널 분위기의 색상·레이아웃·반응형 화면

src/api
  - realApi.js: Spring Boot API, 세션 쿠키와 CSRF 헤더 처리
  - mockApi.js: DB 없이 가입·로그인·채널·메시지 흐름을 재현하는 메모리 mock API
  - index.js: VITE_USE_MOCK_API 설정에 따라 실제 API 또는 mock API 선택
  - mockApi.test.js: Node 내장 테스트 러너로 mock API 흐름 확인

data
  SQLite 파일이 만들어질 로컬 데이터 폴더다. DB 파일은 Git에 올리지 않도록 .gitignore에 제외 규칙을 둔다.

루트 Gradle 파일
  - settings.gradle: Gradle 프로젝트 이름
  - build.gradle: Java/Spring Boot 플러그인, 의존성, Java 버전, 테스트 실행 방식
  - package.json / package-lock.json: React/Vite 의존성과 프런트 실행·테스트 명령
  - vite.config.js: 프런트 개발 서버 설정 및 실제 API용 /api proxy
  - .env.mock: DB 없는 mock 실행 설정
  - README.md: 실행 방법과 API 요약
  - 기획안.md: 제품 범위와 MVP 기준
  - prompt.md: Phase 작업 프롬프트

============================================================
2-A. Java 소스 파일, 클래스, 빌드 결과는 어떻게 다른가
============================================================

간단히 구분하면 다음과 같다.
- .java 파일: 사람이 작성하고 수정하는 Java 소스 코드다. 예: src/main/java/.../SinaeMessengerApplication.java
- class(클래스): 객체와 기능을 묶는 Java 프로그램의 구성 단위다. AuthController, MessageService, UserAccount 등이 클래스다. record로 선언한 AuthResponse도 Java 클래스의 한 종류다.
- .class 파일: Java 컴파일러가 소스 코드를 JVM(Java Virtual Machine)이 읽을 수 있는 바이트코드로 변환한 결과다. 사람이 직접 편집하는 소스가 아니다.
- 빌드: 소스와 설정을 읽어 컴파일하고, 리소스 복사·테스트·실행 패키지 생성 등을 수행하는 과정이다. .class 파일 하나를 뜻하지 않는다.

현재 프로젝트의 실제 대응 예

  소스:   src/main/java/com/sinae/messenger/SinaeMessengerApplication.java
  결과:   build/classes/java/main/com/sinae/messenger/SinaeMessengerApplication.class

package 경로가 build 결과에도 이어지는 것은 Java package 이름으로 클래스를 찾기 때문이다. 이 보고서 작성 시 저장소에서 위 .class 파일과 build/classes/java/test/.../ApiFlowTests.class도 확인했다. 이는 컴파일된 출력이 있다는 뜻이다. 파일이 있다는 사실만으로 현재 소스가 마지막으로 성공적으로 컴파일되었는지, 테스트가 실행되어 통과했는지까지 증명하지는 않는다.

클래스와 파일을 나누는 이유
- 클래스마다 한 가지 주요 책임을 맡기면 찾고 읽고 테스트하기 쉽다. 예를 들어 AuthController는 HTTP 연결, AccountService는 계정 규칙, UserRepository는 사용자 저장·조회 역할이다.
- Java에서 public 최상위 클래스/record는 보통 이름과 같은 .java 파일에 둔다. 예를 들어 public class MessageController는 MessageController.java에 둔다.
- 파일을 나누면 변경 영향과 코드 리뷰 범위를 좁힐 수 있고, 여러 사람이 서로 다른 기능을 작업하기 쉽다.
- 관련 없는 클래스를 한 파일에 몰아넣으면 파일이 커지고 책임이 섞여 수정과 테스트가 어려워진다.
- 내부 클래스가 있으면 한 .java 파일에서 여러 .class가 만들어질 수 있다. 따라서 .java 파일 하나와 .class 파일 하나가 항상 정확히 짝을 이루는 것은 아니다.

Gradle 빌드에서 만들어지는 주요 폴더
- build/classes/java/main: 애플리케이션 .java를 컴파일한 .class 파일
- build/resources/main: 실행에 필요한 설정 등 리소스 복사본
- build/classes/java/test: 테스트 코드를 컴파일한 .class 파일
- build/test-results/test: 테스트 실행 결과 데이터
- build/reports/tests/test: 테스트 결과를 브라우저에서 읽기 쉽게 보여 주는 보고서
- build/libs: 실행 가능한 Spring Boot JAR를 만들었을 때의 패키지 파일

Gradle에서 자주 쓰는 명령
- gradle compileJava: main Java 소스 컴파일
- gradle test: 테스트 코드 컴파일과 테스트 실행
- gradle bootJar: 실행 가능한 Spring Boot JAR 생성
- gradle clean: build 폴더의 생성물을 지운 뒤 새로 빌드할 때 사용

build 폴더는 생성 결과물이므로 보통 직접 수정하거나 Git에 올리지 않는다. 현재 .gitignore도 build/를 제외한다. 코드를 바꿀 때는 src/main/java의 .java를 수정하고, Gradle이 .class를 다시 만들게 한다. IDE에서 .class를 열어도 Java 소스처럼 보이지 않거나 디컴파일된 형태로 보일 수 있는데, 원본 소스 파일과 같은 것은 아니다.

비유하면 .java는 사람이 쓴 조리법, 빌드는 조리 과정, .class는 JVM이 실행할 수 있게 준비된 결과물, 실행 중인 앱은 실제 완성된 음식에 가깝다. 이 비유에서 중요한 점은 결과물을 고쳐도 원본 조리법이 바뀌지 않는다는 것이다.

3. 이 구조의 이름과 실무 사용 여부
============================================================

현재 구조를 쉽게 부르면 “기능별 package 안에 계층을 둔 단일 Spring Boot 백엔드”다.

- 단일 애플리케이션(monolith): API, 인증, 계정, 채널, 메시지가 하나의 애플리케이션으로 함께 실행·배포된다.
- 계층형 구조(layered architecture): API Controller, Service, Repository, Entity처럼 책임을 층으로 나눈다.
- 기능별 package 구성(feature-oriented packaging): user, channel, message처럼 제품 기능에 따라 파일을 가까이 모은다.
- REST API: URL과 HTTP 메서드(GET/POST/PATCH)로 자원을 조회·작성·변경한다.

여기서는 Controller만 api package에 모으고, 각 기능의 Service·Repository·Entity는 user/channel/message package에 둔 혼합형이다. 현업에서도 자주 쓰이는 방식이며, 작은 서비스와 학습 프로젝트에 적절하다. 코드가 커지면 기능별로 controller/service/repository를 더 가까이 묶거나 여러 Gradle 모듈로 나눌 수 있다.

이 구조를 곧바로 “완전한 DDD”, “헥사고날 아키텍처”, “마이크로서비스”라고 부르지는 않는다.
- DDD는 도메인 모델과 업무 언어·경계를 중심으로 설계하는 더 넓은 방법론이다.
- 헥사고날은 외부 기술과 업무 핵심 사이에 포트·어댑터 경계를 명시하는 구조다.
- 마이크로서비스는 독립 배포되는 여러 서비스로 나누는 방식이다. 현재 프로젝트는 하나의 앱이므로 해당하지 않는다.

저장소 전체 관점에서는 백엔드와 프런트엔드가 한 저장소 안에 함께 있는 단일 저장소(full-stack monorepo)다. 개발할 때 Spring Boot와 Vite는 각각 별도 프로세스로 실행된다. 따라서 “저장소가 하나”라는 점과 “백엔드 앱 프로세스가 하나”라는 점은 서로 다른 설명이다.

============================================================
4. API를 이해하고 사용하는 방법
============================================================

API는 화면과 서버가 합의한 요청·응답 약속이다. 보통 다음 정보를 확인한다.
- HTTP 메서드: 조회 GET, 생성 POST, 일부 변경 PATCH
- 경로: 대상이 무엇인지
- 요청: JSON 본문, 경로 변수, 쿼리 문자열
- 인증: 로그인 세션이 필요한지
- 응답: 성공 시 상태 코드와 JSON 모양
- 실패: 잘못된 값, 미로그인, 없는 대상의 상태 코드와 오류 메시지

현재 주요 API

GET    /api/auth/csrf
  변경 요청에 쓸 CSRF 토큰을 받는다. 응답 예: {"token":"..."}

POST   /api/auth/signup
  회원가입. JSON: {"username":"user01","password":"password123"}
  아이디는 영문·숫자·점·밑줄·하이픈으로 3~32자, 비밀번호는 8자 이상이어야 한다.

POST   /api/auth/login
  로그인. 같은 username/password JSON을 보내며, 성공하면 세션 쿠키가 생긴다.

GET    /api/auth/me
  현재 로그인 사용자 조회. 인증이 없으면 401.

POST   /api/auth/logout
  로그아웃. 성공 응답은 본문 없는 204.

PATCH  /api/users/me/nickname
  현재 사용자 닉네임 변경. JSON: {"nickname":"새 닉네임"}

GET    /api/channels
  로그인한 사용자가 공개 채널 목록을 조회한다. 기본 채널은 general과 random이다.

GET    /api/channels/{channelId}/messages
  해당 채널의 메시지를 조회한다. 예: /api/channels/1/messages?limit=50
  처음에는 최신 메시지 최대 50개를 시간순으로 받는다. 다음 조회부터 afterId를 전달하면 그 ID보다 새 메시지만 받을 수 있다. limit은 1~100이다.

POST   /api/channels/{channelId}/messages
  한 줄 메시지 작성. JSON: {"content":"안녕하세요"}
  로그인과 닉네임 설정이 필요하고 빈 내용·줄바꿈·280자 초과는 거부된다.

인증과 CSRF를 함께 쓰는 순서
1. GET /api/auth/csrf를 호출한다. 브라우저는 XSRF-TOKEN 쿠키를 받고 응답 JSON에서 token 값도 읽는다.
2. 회원가입·로그인·닉네임 변경·메시지 작성·로그아웃처럼 상태를 바꾸는 요청에는 쿠키를 함께 보내고 X-XSRF-TOKEN 헤더에 token 값을 넣는다.
3. 로그인이 되면 브라우저가 JSESSIONID 세션 쿠키를 보관한다. 이후 인증이 필요한 요청에도 같은 쿠키가 자동 전송된다.
4. 응답 상태를 먼저 확인한다. 2xx는 성공, 400은 입력 오류, 401은 로그인 필요/인증 실패, 403은 CSRF 토큰 등 권한 문제, 404는 대상 없음, 409는 중복 계정 또는 닉네임 미설정 상태의 메시지 작성 등을 뜻한다.

채널 조회 API는 로그인한 사용자만 사용할 수 있다. “공개 채널”은 채널이 모든 로그인 사용자에게 공개라는 의미이며, 현재 익명 사용자에게 열려 있다는 뜻은 아니다.

API 요청 기본 예시(브라우저 JavaScript)

  const response = await fetch('/api/channels', {
    credentials: 'same-origin'
  });
  if (!response.ok) {
    const error = await response.json();
    throw new Error(error.message);
  }
  const channels = await response.json();

상태 변경 요청은 공통 API 함수가 CSRF 헤더와 JSON 본문을 넣도록 만들면 화면 코드가 단순해진다. 브라우저 개발 도구의 Network 탭에서 URL, 요청 본문, 쿠키/헤더, 응답 상태와 본문을 확인하면 API 문제를 찾기 쉽다. Swagger UI는 http://localhost:8080/swagger-ui.html 에서 요청을 직접 확인하는 데 쓸 수 있다.

============================================================
5. 테스트는 무엇이고 ApiFlow 테스트는 무엇인가
============================================================

테스트는 코드가 기대한 규칙대로 동작하는지 자동으로 확인하는 코드다. 한 번 작성해 두면 수정 뒤에도 같은 확인을 반복할 수 있다.

자주 구분하는 테스트 종류
- 단위 테스트: 함수나 Service 하나를 주변 요소와 분리해 빠르게 확인한다.
- 통합 테스트: 여러 실제 구성요소가 함께 연결되는지 확인한다. 예를 들어 Controller, Security, Service, SQLite를 함께 실행한다.
- 브라우저 E2E 테스트: 실제 브라우저에서 화면을 눌러 사용자 흐름 전체를 확인한다.

현재 ApiFlowTests는 통합 테스트 성격이다. @SpringBootTest로 실제 Spring 애플리케이션 구성을 올리고, @AutoConfigureMockMvc와 MockMvc로 HTTP 요청을 서버 소켓 없이 애플리케이션 MVC 계층에 보낸다. 실제 브라우저나 별도 서버를 통한 E2E 테스트는 아니다.

테스트 파일의 기본 모양

  @Test
  void blankMessageReturnsBadRequest() throws Exception {
      // 준비: 테스트 계정으로 로그인하고 채널 ID를 얻는다.
      MockHttpSession session = signupAndLogin(newUsername());
      String channelId = firstChannelId(session);

      // 실행: 빈 메시지를 전송한다.
      mockMvc.perform(post("/api/channels/{id}/messages", channelId)
                      .session(session)
                      .with(csrf())
                      .contentType(MediaType.APPLICATION_JSON)
                      .content("{\"content\":\"  \"}"))
              // 확인: 서버가 잘못된 요청으로 거절한다.
              .andExpect(status().isBadRequest());
  }

이 흐름은 보통 준비(Arrange) → 실행(Act) → 확인(Assert)이라고 부른다. @Test가 테스트 하나를 표시하고, MockMvc perform이 요청을 실행하며, andExpect가 기대 결과를 비교한다. .with(csrf())는 테스트 요청에 CSRF 토큰을 넣어 실제 보안 설정을 통과하게 한다. .session(session)은 로그인된 브라우저의 세션 쿠키를 흉내 낸다.

현재 ApiFlowTests가 확인하려는 내용
- 회원가입 성공, 중복 아이디 409, 잘못된 입력 400
- 로그인 성공 후 세션으로 현재 사용자 조회, 틀린 비밀번호 401
- 닉네임 변경 후 기존 메시지에도 새 닉네임 표시
- 빈 메시지·280자 초과 메시지 거부, 없는 채널 404
- 로그인하지 않은 채널 목록 접근 401
- 로그아웃 후 인증 세션 사용 불가

@BeforeEach는 각 테스트 전에 메시지·사용자 데이터를 정리한다. 채널은 초기화 코드가 준비하므로 지우지 않는다. 테스트 설정 파일은 개발용 DB와 다른 SQLite 파일을 가리킨다.

프런트엔드 mock 테스트

src/api/mockApi.test.js는 React 화면을 띄우지 않고 mock API 자체의 핵심 흐름을 확인하는 Node 내장 테스트다. 가입·중복 계정 거부·로그인·닉네임 변경·메시지 전송·새 메시지 조회·로그아웃을 한 흐름으로 점검한다. 테스트 라이브러리를 추가 설치하지 않아도 된다.

  npm run test:mock
  npm run build

첫 명령은 mock API 동작 테스트, 둘째는 React/Vite 코드가 브라우저용 파일로 빌드되는지 확인한다. 빌드는 화면이 실제 브라우저에서 기대대로 보이는지까지 증명하지는 않는다.

개발 서버 smoke 확인에서는 `npm run dev:mock` 서버가 HTML과 프런트 모듈을 HTTP 200으로 제공하는 것을 확인했다. mock 흐름 테스트 1건과 Vite 빌드는 통과했다. 실제 브라우저 자동화 테스트는 아직 없다.

Java 21과 build/classes 아래 컴파일 결과를 확인했다. 현재 명령행에서 gradle은 PATH에 없고, JUnit 테스트 결과 보고서도 확인되지 않았다. Gradle 8.14.x 설치 후 Windows Git Bash에서 백엔드 테스트를 실행한다.

  gradle test
  gradle test --tests 'com.sinae.messenger.ApiFlowTests'
  gradle bootRun

첫 명령은 전체 JUnit 테스트, 둘째는 ApiFlowTests만, 셋째는 백엔드 실행이다. JUnit 테스트 코드는 작성되어 있지만 실제 통과 결과는 아직 확인되지 않았다. 프런트 mock 테스트 결과와 백엔드 JUnit 결과는 별도로 본다.

============================================================
6. 클라이언트는 어떻게 설계하면 좋은가
============================================================

클라이언트는 `src/ui/App.jsx`, `src/ui/styles.css`에 구현되어 있다. `src/api/realApi.js`는 실제 Spring API를 호출하고, `src/api/mockApi.js`는 DB 없이 화면을 확인하도록 응답을 흉내 낸다. 다음은 코드의 주요 UI 책임을 설명한 것이다.

- App: 로그인 여부와 전체 화면 흐름을 선택
- AuthForm: 회원가입·로그인 입력
- NicknameForm: 최초 닉네임 설정 및 변경
- ChannelList: GET /api/channels 표시와 채널 선택
- ChatView: 현재 채널, 메시지 목록, 입력창
- MessageList: 작성자·시간·내용 표시
- MessageComposer: 한 줄 입력과 전송
- api.js: fetch, CSRF, 세션 오류, 공통 오류 처리

먼저 화면에서 쓸 상태를 정한다.
- user: 현재 로그인 사용자 또는 null
- channels: 채널 목록
- selectedChannelId: 선택된 채널
- messages: 화면에 보여 줄 메시지 목록
- loading/error: 기다리는 중인지, 오류가 있는지
- draft: 입력 중인 메시지

앱 시작 시 CSRF 토큰을 준비하고 GET /api/auth/me를 호출한다. 200이면 로그인 화면을 건너뛰고, 401이면 로그인/회원가입 화면을 보여 준다. 로그인 뒤 닉네임이 비어 있으면 닉네임 설정 화면을, 닉네임이 있으면 채널 화면을 보여 준다.

메시지 갱신은 WebSocket 없이 polling으로 한다.
1. 채널을 처음 열 때 GET .../messages를 호출한다.
2. 가장 큰 메시지 id를 기억한다.
3. 예를 들어 몇 초 간격으로 ?afterId=마지막ID를 붙여 새 메시지를 요청한다.
4. 새 결과를 목록에 이어 붙이고 마지막 ID를 갱신한다.
5. 채널을 바꾸거나 화면을 나갈 때 setInterval을 정리한다. 정리하지 않으면 이전 채널 요청이나 타이머가 계속 남을 수 있다.

전송 중에는 버튼을 잠시 비활성화하고, 성공하면 입력값을 비우고 새 메시지를 목록에 추가한다. 실패하면 입력을 잃지 않게 하고 사용자에게 오류를 보여 준다. 401이면 로그아웃 상태로 되돌릴 수 있다.

Vite proxy는 `vite.config.js`에 설정되어 있으며 실제 모드의 `/api` 요청을 백엔드 `localhost:8080`으로 전달한다. DB 없이 화면을 볼 때는 `.env.mock`과 `npm run dev:mock`을 사용한다. 실제 API 모드 `npm run dev`는 Spring Boot와 SQLite 연결이 가능해야 한다.

화면 구조와 서버 호출을 분리하는 이유는 UI를 바꾸더라도 API 처리 로직을 재사용하고, 서버 오류 처리도 한곳에서 관리하기 위해서다. 처음부터 상태관리 라이브러리를 더하지 말고 React state와 effect로 시작한 뒤 복잡도가 실제로 커질 때만 확장한다.

7. 새 API를 추가할 때의 기본 틀
============================================================

예를 들어 “현재 사용자 닉네임 변경”은 다음 책임 분리로 추가돼 있다.

1. NicknameRequest: JSON 입력값과 길이·빈 값 규칙
2. UserController: PATCH URL과 요청/응답을 연결
3. AccountService: 닉네임 변경 업무 처리
4. UserRepository: 사용자 데이터 조회/저장
5. AuthResponse: 클라이언트에 반환할 공개 사용자 정보
6. ApiFlowTests: 성공·잘못된 입력·인증 여부를 검증

새 기능을 만들 때도 순서대로 생각하면 된다.
- 어떤 URL과 HTTP method인가?
- 로그인한 누구에게 허용되는가?
- 요청 데이터와 검증 규칙은 무엇인가?
- 업무 규칙과 실패 조건은 무엇인가?
- DB는 어떤 데이터를 저장·조회하는가?
- 성공/실패 응답은 어떤 상태 코드와 JSON인가?
- 이를 확인하는 테스트가 있는가?

DB Entity를 그대로 JSON으로 반환하지 말고 요청 DTO와 응답 DTO를 따로 둔다. Entity는 DB 관계와 저장에 맞추고, DTO는 API 약속에 맞춘다. 그러면 내부 DB 구조를 바꾸어도 클라이언트와 주고받는 형식을 덜 흔들 수 있다.

8. 현재 상태와 다음 단계
============================================================

현재 구현됨
- Gradle 기반 Spring Boot 백엔드 기본 구조
- SQLite 파일 설정과 기본 공개 채널 초기화
- 회원가입, 세션 로그인·로그아웃, 현재 사용자, CSRF API
- 닉네임 변경, 채널 목록, 메시지 조회·작성 API
- 요청 검증, 공통 오류 응답, OpenAPI 설정
- API 통합 흐름 테스트 코드
- React/Vite 터미널 UI와 실제 API 클라이언트
- DB 없는 메모리 mock API 및 Node 내장 mock 흐름 테스트
- `npm run build`와 mock 테스트 실행 확인
- Vite 개발 서버 HTML·프런트 모듈 HTTP 응답 확인

아직 없음 / 확인 필요
- 실제 프런트엔드 ↔ Spring API ↔ SQLite 통합 흐름 검증 (DB 작업은 사용자 지시에 따라 마지막 단계로 보류)
- 명령행 Gradle 실행 및 JUnit 결과 확인 (현재 .class 파일만으로 테스트 통과를 판단할 수 없음)
- 브라우저 상호작용 자동화 테스트
- SQLite 파일을 배포 환경에서 보존하는 방식과 운영 DB 선택
- 실제 클라우드 배포

현재 우선순위는 `npm run dev:mock`으로 프런트 흐름을 확인하고 `npm run test:mock`, `npm run build`를 반복하는 것이다. 사용자가 DB를 마지막에 진행하기로 했으므로 실제 SQLite/JUnit/API 통합 검증은 프런트 확인 이후 수행한다. 이후 마지막 통합 단계에서 Gradle 실행 환경을 확인하고, Spring API와 SQLite를 연결한 핵심 흐름을 검증한다. Docker는 사용하지 않는다. 클라우드 배포는 대상·방식 결정과 별도 사용자 승인 전까지 진행하지 않는다.
